# ARC engine guide

ARC is a small game engine written from scratch in C11, with no external libraries. It is built for three things:

- **Performance.** Data-oriented design, no hidden allocations, and instanced rendering. Thousands of objects take a handful of draw calls.
- **Adaptability.** One header, one unity file and four interchangeable backends. Games are four callbacks.
- **AI use.** An agent can build, run, drive, inspect and screenshot a game from the command line, without a display. Runs are deterministic, so they can be replayed and compared.

## Building

| Target | Command | Output |
|---|---|---|
| Linux (X11/GL) | `./build.sh linux [game.c]` | `build/<game>` |
| Headless only | `./build.sh headless [game.c]` | `build/<game>_headless` |
| Windows (MSVC) | `build.bat [game.c]` in a VS Developer Prompt | `build\<game>.exe` |
| Windows (MinGW cross) | `./build.sh win [game.c]` | `build/<game>.exe` (static, about 750 KB) |
| Web | `./build.sh web [game.c]` (needs emsdk) | `build/web/<game>.html`, `.js`, `.wasm` (about 210 KB) |
| Self-test | `./build.sh test` / `build.bat test` | prints `ARC test OK n/n` |

**Using ARC in another project.** Run `python tools/new_game.py <folder>`. See [SHARING.md](SHARING.md) for shared vs vendored copies and versioning.
The game's `build.bat` / `build.sh` build Windows, Linux, headless and web (`web`: `build/web/index.html`), and
`release` builds Windows and web and writes `dist/<Title>-windows.zip` (exe + assets) and `dist/<Title>-web.zip`
(files at the top level), the two uploads an itch.io page needs. `new_game.py <folder> --update-scripts` brings an
older game's scripts up to date (the old ones are kept as `build.bat.old` / `build.sh.old`). A game can have its own
web page in `web/shell.html`; ARC's default shows a progress bar (no words), uses the game's title for the tab and
stops Space, Tab, arrows and Page keys from scrolling the page around it.

**Running a web build.** Serve the folder over HTTP (`python -m http.server -d build/web`); browsers won't load WASM from `file://`. URL query arguments become `argv`, for example `demo.html?--seed=3&--mute`.

**Debug builds.** `DEBUG=1 ./build.sh headless` builds with AddressSanitizer and UndefinedBehaviorSanitizer. The sample and the self-test run clean.

## A game in four callbacks

```c
#include "arc.h"
static void init(void)        { /* create meshes, pools, vars */ }
static void tick(void)        { /* game logic, fixed step: arc_dt() seconds */ }
static void draw(float alpha) { /* camera + draw calls; alpha in [0,1] blends previous -> current tick */ }
static void dump(arc_json *j) { /* write game state for agents and tests */ }
arc_app arc_main(int argc, char **argv) {
    return (arc_app){ .title = "Game", .init = init, .tick = tick, .draw = draw, .dump = dump };
}
```

Optional members of `arc_app`:

| Member | Purpose | Default |
|---|---|---|
| `width`, `height` | window size | 1280×720 |
| `tick_hz` | simulation rate | 60 |
| `clear_color` | background colour | — |
| `perm_mb`, `frame_mb` | arena sizes | 64 / 16 |
| `shutdown` | called on exit | — |
| `command` | custom agent commands | — |

## Architecture

### Frame loop

Each frame the platform pumps input into a raw state. The core then runs some number of fixed ticks:

- **Windowed:** an accumulator decides, catching up at most 8 ticks.
- **Headless or `--stdin`:** exactly 1 tick.

Before each tick the core does three things:

1. Executes due agent commands.
2. Snapshots input (raw keys OR'd with scripted keys, or the replay stream). The snapshot is recorded if `--record` is on,
   and kept in memory so `seek`/`rewind` can re-simulate.
3. Calls `tick()`, then updates what the engine runs on its own: the UI (widgets record their drawing), particles, and
   positional audio. Games with `save_state` get a snapshot every 60 ticks (thinned as the run grows).

After the ticks, `draw(alpha)` fills the draw lists, and the front end sorts them and hands one `arc__frame_data` to the backend. Headless runs skip `draw` completely unless a screenshot is taken (`shot` draws there and then), so simulations run at full CPU speed. SWARM simulates around 60,000 ticks a second headless.

**Immediate mode** (`arc_app.immediate = true`) is for games whose screens take input while they draw (immediate-mode UI, ports from raylib-style loops). `tick()` draws as well and `draw` is not called. Every tick builds a frame: its render-target passes always run, so cached targets (a floor layer that decals accumulate on, say) stay right, and the screen shows the last tick's frame. Headless, only the target passes run unless a screenshot is due. Moonbase Raid runs this way.

`init()` may draw into render targets in either mode, to bake art at load; its screen drawing is dropped.

A frame is a list of **passes**: the screen, then one pass per `arc_target_begin`…`arc_target_end` (targets nest), each with its own camera, lights, clip and blend state as they were set inside it.

### Determinism

The simulation depends only on four things:

- the tick count;
- the per-tick input snapshot;
- the seeded PCG32 generator;
- the game's own code.

Replays store only input changes, so a 10-minute session is a few KB. The same run produces the same game state in all four backends. The Linux GL, Windows D3D11, WebGL2 and software screenshots of the sample match.

### Rendering

| Stream | How it's drawn |
|---|---|
| Meshes | Uploaded once to GPU buffers (vertices with position, normal, colour, texture coordinates; skinned meshes add 4 joints and weights). Each `arc_draw_mesh*` appends a 144-byte instance (4×4 matrix, tint, emissive, tint mix, whiten, alpha, first bone, and the effects: dissolve, hologram, outline, texture scroll). At frame end, solid instances are grouped by mesh with a stable counting sort and uploaded in one buffer write. Each mesh is then one instanced draw call; mirrored instances get their own batch, wound the other way. |
| See-through meshes | `arc_draw_mesh_alpha` / `_additive` / `_styled` instances are sorted back to front (stable merge sort on distance from the eye) and drawn after the solid meshes, immediate triangles and lines, with depth testing but no depth writes. |
| Skinning | `arc_anim_pose` blends clips into joint matrices on the CPU; drawing a posed mesh appends its skinning matrices (3×4 each) to a per-frame bone list. The GPU backends read it from a 1536×128 float texture in the vertex shader, so posed instances still batch; the software renderer skins on the CPU. |
| Immediate triangles | Rebuilt every frame for procedural shapes. One buffer, one draw, double-sided. |
| Lines | One dynamic buffer, one draw. |
| 2D triangles | Rectangles, sprites, text and `arc_draw_triangles2d` go into one buffer. Batches break when the texture, blend mode or clip rectangle changes. |
| Render targets | A texture with its own depth buffer. GL draws targets upside down so every texture's first row is its top, as in D3D and the software renderer. |
| Particles | Simulated in `tick` by the engine; `arc_draw_particles` appends one unlit camera-facing quad instance per particle to the see-through stream (sorted like any see-through mesh). |
| Shadows | Per pass with shadows on: the solid batches are drawn once more, depth only, from the light into a shadow map (an orthographic box around `arc_set_shadows`' centre, snapped to whole texels). Lit pixels look it up with a 3x3 grid of linear comparison samples. With cascades, 2 or 3 boxes (each the bounding sphere of a slice of the camera's view, so its size never changes) share a 2x2 atlas; a pixel uses the first that holds it and blends into the next near its edge. Softness widens the filter to a 5x5 tent. |
| Post-processing | With `arc_set_post` on, the screen's 3D renders into an HDR buffer (16-bit float, multisampled when MSAA is on). Bloom: a bright pass and 5 half-size levels down, a tent filter back up. SSAO: one pass over the depth buffer (sample 0 when multisampled) into an AO buffer, blurred in the composite. The composite (CRT curve, pixelate, FXAA, aberration, tilt-shift, AO, exposure, bloom, ACES tone curve, desaturate, contrast, colour table, vignette, scanlines) writes the screen, and only then is the screen's 2D drawn. |

Shading (the same formula in all four renderers):

- Per pixel: Lambert lighting from one directional light and up to 16 point/spot lights, plus ambient, emissive, an optional rim light, and linear or exponential fog.
- Meshes with a material: the normal map bends the normal in a frame worked out from the triangle (no stored tangents); PBR ones use GGX highlights, Fresnel and an environment gradient (`arc_internal.h` has the formulas); the emissive map adds light.
- The albedo is the vertex colour times the mesh's texture (white when it has none). Solid meshes cut out texels with alpha below 0.5; see-through meshes multiply in the texture's and vertex colours' alpha.
- Textures can be smooth, repeating and mipmapped (`ARC_TEX_*`). GPU backends use trilinear filtering; the software renderer picks one mip level per triangle.
- Shadows remove the directional light's contribution (times `arc_set_shadow_strength`), never the ambient.
- Unlit instances (particles) are `colour × (1 + glow)`; additive ones fade to black in fog instead of toward the fog colour.
- `arc_app.msaa = 4` multisamples the screen: an MSAA framebuffer resolved at the end of the frame on desktop GL and D3D11, the browser's antialiased canvas on the web (and a multisampled HDR buffer whenever post-processing is on).

### Memory

| Allocation | Lifetime |
|---|---|
| `arc_perm()` arena | Lives for the whole program; use it for pools and level data. |
| `arc_frame()` arena | Reset every frame; use it for temporary strings (`arc_fmt`) and scratch arrays. |
| Engine draw buffers | Allocated once at startup. |

`arc_pool` stores fixed-size items with generation-checked handles, so stale references return `NULL` instead of corrupting memory.

Conventions:

- The world is right-handed and +Y is up.
- Colours are `0xRRGGBB`; an alpha byte of 0 means opaque. Use `arc_rgba(rgb, a)` when you need alpha.
- Matrices are column-major.

## The agent interface

See [AGENTS.md](../AGENTS.md) for the full command list. In short:

- **Inputs:** `--cmd "..."`, `--script file`, or `--stdin` for an interactive session, with any binary and any backend. On the web, call `Module.arcCommand("...")` from the page's JavaScript.
- **Outputs:** one-line `ARC <kind> ...` records on stdout, JSON dumps (engine stats, profiler zones, vars and your `dump()`), and PNG screenshots.
- **Control:** scripted keys and mouse, tunable vars, custom game commands, seeds, record and replay.
- **0.5:** `ui` / `ui_click LABEL` (widgets by name), `gif` / `shots` (motion), `compare REF.png` (screenshot regression),
  `seek` / `rewind` / `state_save` / `state_load` / `state_check` (time travel, with the game's state callbacks),
  `inspector`, `reload` (with `--hot`).

## Performance notes

Measured with SWARM's `--bench N` mode: N spinning meshes, each with its own matrix computed every frame.

| Objects | Draw calls | `draw()` (game code) | sort and upload prep |
|---|---|---|---|
| 1,000 | 4 | 0.05 ms | 0.01 ms |
| 10,000 | 4 | 0.37 ms | 0.16 ms |
| 50,000 | 4 | 4.5 ms | 1.3 ms |

That works out to about 0.1 µs per object on the CPU side. The GPU cost depends on the hardware. These figures came from a cloud machine with only a software GPU, so the frame times reported there are not representative.

Tips:

- Draw the same mesh many times instead of building many small meshes.
- Keep per-object work in `tick` as plain loops over pools. Avoid pointer-chasing graphs.
- Wrap suspicious code in `ARC_PROF("name")` and read the zones with `stats`.

## File formats

**`.arcm` mesh** (version 3; versions 1 and 2 still load)

- Header (32 bytes): `"ARCM"`, `u32` version, `u32` vertex count, `u32` index count, `u32` flags (1 skinned, 2 double-sided, 4 16-bit indices), `u32` texture bytes, two `u32` zeros.
- Version 3: the bounds (`f32 lo[3], hi[3]`), then compact vertices of 16 bytes: `u16 pos[3]` (0..65535 across the
  bounds), `s8 normal[2]` (octahedral), `u8 rgba[4]`, `f16 u, v`. Expanded to `arc_vertex` at load; position error
  below 1/65535 of the model's size, normals within a degree. About 40% smaller files than version 2.
- Version 2: vertices `{f32 pos[3], f32 normal[3], u8 rgba[4], f32 u, v}`, 36 bytes each (`mesh2arcm.py --v2`).
- Skinned: `{u8 joints[4], u8 weights[4]}` per vertex, weights summing to 255.
- Indices (`u32`, or `u16`), padded to 4 bytes, then the texture file (PNG, QOI or baseline JPEG).
- Material (0.6; header byte 24 = its size, 0 = none): `"MATL"`, `u32` 1, `u32` flags (1 = PBR), `f32` normal scale,
  metallic, roughness, occlusion strength, emissive r, g, b, `u32` sizes of the normal, ORM and emissive images, then
  the images (PNG or JPEG, laid out like the colour texture). Older ARC skips it.
- Glow mask (0.10.15, after everything else): `"GLOW"`, `u32` size, then the image (PNG, lossless). Its red, green and
  blue mark three groups of glowing pixels (`arc_mesh_style.glow`); `arc_mesh_glow_mask` reads it. Older ARC never reads that far.

Make them with `tools/mesh2arcm.py`. Its glTF/GLB reader is built in (numpy and Pillow): textures (kept as JPEG when
possible), vertex colours, skins and animations. `--footprint/--height/--size`, `--yaw`, `--flat`, `--texture-size`,
`--glow-mask IMG`, `--batch DIR OUT`. OBJ is read too, and other formats through `trimesh` if it is installed.

**`.arca` animation**: `"ARCA"`, `u32` version = 1, joint and clip counts, a root matrix, then per joint a name, parent,
inverse bind matrix and rest transform, then per clip a name, rate, frame count and every joint's translation, rotation
and scale per frame. `mesh2arcm.py rig.glb out.arcm --anim out.arca clip1.glb clip2.glb ...` writes one from a rigged
GLB and its animation files (clips matched to the rig by joint name; Ludo's rig + animation presets work as is).

**`.arcpak` asset pack**: `"ARCP"`, `u32` version = 1, `u32` file count, `u32` directory bytes; per file `u32` offset,
`u32` stored size, `u32` size, `u8` method (0 stored, 1 zlib), `u8` name length, the name; then the data. Every loader
looks in mounted packs before the disk, by relative path; `assets.arcpak` beside the program mounts itself.
`tools/arcpak.py assets.arcpak assets` makes one (zlib where it saves at least 3%). Evolution's web assets go from
8.0 MB (.arcm v2, loose files) to 6.5 MB (v3) to 4.2 MB (v3 in a pack).

**Game state snapshots** (`state_save FILE`): `"ARCS"`, `u32` version, `u64` tick, the `arc_rand` state, the input
snapshot, the arc_var values, `u64` size and the game's own `save_state` bytes. Valid for the same build only.

**Replay**

- Header: `"ARCR"`, then `u32` version, `u64` seed, `u32` tick rate.
- Then records `{u32 tick, input snapshot}`, written only when the input changes.
- Then an end marker.

**Screenshots** are RGB PNGs. Textures can be PNG (8-bit, non-interlaced, any colour type), QOI or JPEG (baseline and
extended sequential, any chroma subsampling: ARC's own decoder in `src/arc_jpeg.c`; progressive JPEGs are refused).

**Audio**: MP3, QOA and 16-bit WAV, mono or stereo, any sample rate (the mixer resamples while it plays). Sounds
are decoded whole when loaded; music stays compressed in memory and is decoded a frame at a time.

- **MP3** (`src/arc_mp3.c`): ARC's own decoder for MPEG-1, MPEG-2 and MPEG-2.5 Layer III: mono/stereo, mid/side and
  intensity stereo, long/short/mixed blocks, CBR, VBR and free-format bitrates, streams that switch between mono and
  stereo. ID3v2 tags are skipped. A Xing/Info frame with a LAME tag (LAME and FFmpeg write one) gives the exact
  length, so files are trimmed exactly as FFmpeg trims them and music loops without a gap. It passes all 13 of the
  ISO/IEC 11172-4 Layer III conformance streams at full accuracy (no sample off by more than 1) and matches FFmpeg
  to within 1 on 44 test files. The standard's numeric tables (Huffman codes, band widths, synthesis window) are in
  `src/arc_mp3_tables.h`, written by `tools/mp3_tables_gen.py`. Decoding runs about 200x real time on one core.
  Layers I and II are not supported.
- **QOA** decodes faster still and suits many sounds playing at once; `tools/audio_convert.py` makes it (and is the
  way in for OGG and FLAC).

## Extending ARC

**A new render backend** (Vulkan, Metal, D3D12):

1. Implement `arc__backend` in `src/arc_internal.h`. It has 12 functions; the main one renders a whole `arc__frame_data`
   (passes with their own shadow and post-processing settings).
2. Use `arc_gl.c` as a template, about 750 lines; `arc_soft.c` is the reference for every formula.
3. Select it from the platform's `init`.

**A new platform:** implement `arc__platform` (init, poll, present, shutdown, time, sleep) and call `arc__run()` from `main`.

**Engine features** belong in the core only if a second game needs them. Keep game-specific systems in game code.

## Limits and roadmap

Version 0.6 does not yet include:

- several textures or materials per mesh (one texture and one material each; `mesh2arcm.py` packs several into one);
- shadows from point and spot lights, or more than 16 of them lighting one pass;
- image-based lighting from real environment maps (reflections use a 3-colour gradient);
- rigid-body physics (ARC has collision queries and a character controller; dynamics are the game's);
- more than one gamepad, or rumble;
- IME / compose text input on the web (keys that type a character directly work);
- an AudioWorklet on the web (it still uses the deprecated ScriptProcessorNode, which every browser runs);
- OGG Vorbis (convert with `tools/audio_convert.py`);
- hot reload on the web (desktop only: assets with `--hot`, code with the `hot` builds);
- multithreaded job system;
- macOS.

Suggested next steps:

1. Multiplayer (0.7): a relay server (UDP desktop, WebSocket web, room codes), command relay for turn-based games,
   rollback for real-time ones on top of `save_state`/`load_state`, determinism hardening, loopback tests for agents.
2. Job system for `tick` and the instance build.
3. Shadows from spot lights.
