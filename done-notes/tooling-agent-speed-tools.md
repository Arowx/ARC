# Request from Allan (tooling): agent speed tools: arc_brief, arc_report and a one-call MCP check

**Why.** Allan asked whether to build a mini AI code editor for ARC. We decided against it: Claude Code, Cursor and
VS Code already do the editor part, and ARC's headless loop, `dump`/`frame`, arc-check and MCP server are the parts
that matter. The time an agent loses on an ARC game goes to three other things:

1. **Getting up to speed.** Every new session re-reads `main.c` to find the `dump()` fields, the debug commands, the
   tunables, the acceptance status and the ARC version the game needs. On Droids, Moonbase Raid or HEATLINE that
   takes many reads before any real work starts.
2. **Analysis spread across tools.** Doctor, arc-check, `sweep.py` and `sessions.py` each give part of the picture,
   with no single summary of how a game is doing.
3. **Small MCP round trips.** `arc_command` already takes a `;` script, but build → script → check still takes
   several calls (`arc_build`, `arc_start`, `arc_command`, then `arc_expect` once per check).

**Ask.**

1. **`tools/arc_brief.py [GAME_DIR] [--out BRIEF.md] [--json]`**: writes a short brief of a game (aim for under
   ~150 lines), read by agents first. It should list:
   - title, ARC path (`arc.txt`, or vendored) and the ARC version the game assumes (the `ARC_HAS_*` macros it uses);
   - source files with line counts, and where `init` / `tick` / `draw` / `dump` / `command` / `save_state` live (file:line);
   - the `dump()` schema: the field names it writes, taken from a real headless `dump` after `step 60` when a
     headless build exists, otherwise read from the source;
   - debug commands handled in `command()`;
   - tunables (`arc_var` names and defaults);
   - named meshes, loaded assets (count by kind), templates or features used (board, nav, physics, net mode...);
   - each acceptance block's pass/fail status when `--check` is given;
   - open `request` issues for this game.
   Have `new_game.py` mention it in the game's `AGENTS.md`, and add an `arc_brief` MCP tool returning the same text.
2. **`tools/arc_report.py [GAME_DIR] [--seeds 1-20] [--frames N] [--field ...] [--sessions]`**: one health report.
   It runs, in order:
   - doctor (errors and warnings);
   - `warn_check` on the game sources;
   - every acceptance file (blocks passed out of total);
   - `state_check` when the game has save_state;
   - an optional seed sweep with min/median/max of the given fields;
   - a summary of the newest play session (events, F8 marks, with the replay command for each).
   Output is a short markdown report plus `--json`; exit 1 on any failure.
3. **MCP `arc_run`** (or an option on `arc_command`): build if sources changed, start headless if not running, run a
   `;` script and test a list of `expect` lines (arc-check syntax) in **one call**. It returns pass/fail per line and
   only the dump/frame paths those lines asked for. Also add `arc_report` / `arc_brief` as MCP tools.

Must not change: existing tool flags and output, arc-check syntax, and no new dependencies (standard library only,
as with the other tools).

**Game side.** None needed: these are tools. Droids, Moonbase Raid and HEATLINE would be the first games to try them
on. Workaround meanwhile: agents read the source by hand.

## Acceptance

Run on the `tactics` template (and a sample) as part of `build.sh test`:

```sh
python3 tools/new_game.py /tmp/briefgame --template tactics
python3 tools/arc_brief.py /tmp/briefgame --json   # lists init/tick/draw/dump/command locations, >= 1 dump field,
                                                    # >= 1 debug command, >= 1 tunable, the ARC version
python3 tools/arc_report.py /tmp/briefgame          # exit 0; reports doctor, warn_check, acceptance N/N, state_check
```

The game itself must still pass its own checks:

```arc-check
game samples/board/board.c
do step 60
expect tick >= 60
```

MCP: `arc_run` with `script: "step 60; dump"` and `expect: ["tick >= 60"]` returns one PASS in a single call.

## Done in ARC 0.10.16

- **`tools/arc_brief.py`**, as asked.
  - It covers the title, the ARC path and its version, file line counts, the callback locations (`file:line`), the
    `dump()` schema, commands (with how many words each takes), tunables and their defaults, named meshes, assets by
    kind, engine features, acceptance results with `--check`, and open `request` issues.
  - **The dump schema** comes from a real headless run after `step 60` when a headless build exists, otherwise from
    the source; `--no-run` forces the source.
  - **One addition, "Needs ARC x.y.z or later":** the templates use no `ARC_HAS_*` macros, so the macros alone said
    little. The brief also dates each engine call the game makes from `arc.h`'s version notes and the `ARC_HAS_*`
    comments, and names the newest. The tactics template needs 0.10.14 (`arc_popup_text`, `arc_play_var`,
    `arc_yaw_to`).
  - **Size:** the tactics template's brief is 45 lines. `--json`, `--out BRIEF.md`, and `--no-net` to skip GitHub.
  - It works on a game folder or on a `.c` file in ARC's repo (`samples/board/board.c`).
- **`tools/arc_report.py`**, in the order asked: doctor, `warn_check` on the game's C sources (MSVC when `cl` is on
  the PATH), every acceptance file (failed blocks named), `state_check`, `--seeds` / `--frames` / `--field` / `--cmd`
  sweep (min / median / max), and `--sessions` (the newest session's events and each F8 bookmark with its replay
  command). Markdown or `--json`; exit 1 on any failure. About 30 s on the tactics game.
- **MCP:**
  - **`arc_run(script, expect, args, build, source, exe, restart)`** builds when the game's or ARC's sources are newer
    than its headless exe, starts the game when it isn't running (or was rebuilt, or the args changed), runs the
    script, and tests the `expect` lines in one call.
    - It returns `PASS` / `FAIL` per line with the value each path holds, e.g. `FAIL game.units[0].x == 5   (game.units[0].x = 2)`.
    - Called again without `exe`, it keeps the running game and its flags.
    - Every step is recorded for `arc_save_check`.
  - **`arc_brief`** and **`arc_report`** are MCP tools too; `arc_report` stops the running game first, because the
    build replaces its exe.
  - The server's instructions point agents at `arc_brief` and `arc_run` first.
- **`new_game.py`** puts a "Start here" paragraph at the top of each new game's `AGENTS.md`. `--update-scripts` adds the
  same note to an existing game's `AGENTS.md` once, so Droids, Moonbase Raid and HEATLINE get it with
  `python <ARC>/tools/new_game.py <game> --update-scripts`.
- **Nothing existing changed:** no existing tool flags, outputs or arc-check syntax, and no new dependencies.
- **Your acceptance:**
  - `tests/agent_tools_test.py` runs in `build test` on both platforms. It makes a tactics game and checks the
    brief's locations, dump fields, commands, tunables and ARC version. It checks that the report exits 0 with doctor,
    warnings, acceptance N/N and `state_check`, and that a check broken on purpose makes the report exit 1. It also
    briefs `samples/board`.
  - The `samples/board` arc-check is `tests/agent_tools_check.md`.
  - `tests/mcp_test.py` calls `arc_run` with `script: "step 60; dump"` and `expect: ["tick >= 60"]` and gets one
    PASS in a single call.
- **Not tried yet:** the real Droids, Moonbase Raid and HEATLINE folders, which are on the PC. Run
  `arc_brief.py --check` on them, and tell me what it gets wrong.
